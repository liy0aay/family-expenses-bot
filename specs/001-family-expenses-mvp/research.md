# Research: Сервис учёта семейных расходов

Все NEEDS CLARIFICATION отсутствуют — ключевые решения заданы спекой и конституцией. Ниже — фиксация решений с обоснованием (формат: Decision / Rationale / Alternatives).

## 1. Архитектура: единый Go-сервис

- **Decision**: один процесс `cmd/server/main.go`: HTTP REST (ogen) + Telegram Long Polling поверх общего `internal/service`. Оркестратор агента — `internal/agent` (вне `adapter/`).
- **Rationale**: одна семья и скромная нагрузка — отдельные сервисы дают только расходы на эксплуатацию; общий домен гарантирует единые правила (права, деньги, категории) для бота и панели; `docker compose up` поднимает всё (конституция VI).
- **Alternatives considered**: два сервиса (bot-api + panel-api) — дублирование домена или выделение общей библиотеки без выигрыша; serverless/функции — несовместимо с Long Polling и compose-требованием.

## 2. REST-кодогенерация: ogen (ADR-002)

- **Decision**: сервер и роутер генерируются ogen'ом из `api/openapi.yaml` (строго OpenAPI 3.0.3), версия зафиксирована в `go.mod`, повторная генерация даёт пустой diff (CI проверяет `git diff --exit-code`). Валидация запросов — по схеме; маппинг ошибок домена в HTTP — один хелпер в `adapter/rest`.
- **Rationale**: типизированные хендлеры и валидация из контракта устраняют рассинхрон «документация ↔ код»; ogen — роутер API-путей, а stdlib mux монтирует его под `/api/v1/` (ogen игнорирует префикс из `servers` — ADR-008) и держит служебный healthz.
- **Alternatives considered**: oapi-codegen (в т.ч. strict-server) — валидация требует внешнего middleware (kin-openapi) в рантайме и отдельного роутера (отклонён, ADR-002); chi + ручной маппинг — контракт неизбежно расходится с кодом.

## 3. Доступ к БД: pgx/v5 + sqlc, миграции goose (ADR-003)

- **Decision**: PostgreSQL 16, pgx/v5 (пул), типобезопасные запросы генерируются sqlc, миграции — goose SQL-файлы с embed.
- **Rationale**: SQL остаётся явным и проверяемым компилятором; домен не загрязняется ORM-моделью; goose — минимальный инструмент без фреймворка.
- **Alternatives considered**: GORM/ent — утечка модели БД в домен и рефлексия; squirrel — конкатенация SQL руками, без типобезопасности; golang-migrate — равноценен, goose проще в go-тулинге.

## 4. Telegram-транспорт: минимальный Long Polling клиент (ADR-004)

- **Decision**: собственный минимальный клиент Bot API на `net/http`: `getMe`, `getUpdates` (long poll), `sendMessage`. Горутина polling с `recover()` (падение бота не роняет HTTP-сервер). Пустой `TELEGRAM_BOT_TOKEN` — WARN «starting in Web-API only mode».
- **Rationale**: нужны 3 метода — SDK не оправдан; Long Polling не требует публичного хоста и TLS (в отличие от webhook); полный контроль таймаутов и ошибок.
- **Alternatives considered**: go-telegram-bot-api / telebot — лишние зависимости и абстракции; webhook — требует публичного HTTPS-эндпоинта, противоречит «поднял и работает локально».

## 5. LLM-клиент: минимальный OpenAI-совместимый (ADR-005)

- **Decision**: собственный клиент `chat/completions` (OpenAI-совместимый) на `net/http`; конфиг `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`; каждый вызов логируется slog (модель, длительность, число тул-вызовов — без содержимого переписки на уровне INFO).
- **Rationale**: нужен один эндпоинт с tools; свой клиент даёт полный контроль парсинга аргументов тулов (обязательно `json.Number` для `amount_rub`) и не добавляет зависимость.
- **Alternatives considered**: sashabaranov/go-openai — зрелая, но тянет промежуточные типы и усложняет контроль парсинга аргументов; LangChain-подобные оркестраторы — избыточны для 5 тулов.

## 6. Деньги: RublesToKopecks — единственная точка конвертации

- **Decision**: на границе тулов сумма — `amount_rub` (number). Адаптер парсит аргументы как `json.Number`: рубли и копейки отдельно, без float64 и math.Round; больше двух знаков после точки → `invalid_amount`. БД и REST-ответы оперируют только `amount_minor` (int64, копейки); REST-запросы (POST/PATCH) принимают `amount_rub` десятичной строкой — конвертация той же функцией, единая валидация с ботом (FR-019).
- **Rationale**: конституция II запрещает float64 для денег; `json.Number` сохраняет исходное представление; единственная функция конвертации = единая точка тестирования (350 / 350.5 / 350.50 / 0.01 / 350.505 → reject).
- **Alternatives considered**: парсинг через float64 + округление — теряет точность на 350.505, запрещён конституцией; строковый формат в схеме тула — хуже для LLM-вызовов, number согласован с ТЗ.

## 7. Память диалога: in-memory (ADR-006)

- **Decision**: `internal/agent/memory`: map по chat_id, окно 8 последних сообщений (включая результаты тулов), TTL 30 мин с последней активности, оба параметра настраиваются. Хранит упомянутые `expense_id` для ссылки «последнее» и кандидатов удаления.
- **Rationale**: процесс один (ADR-001) — Redis не нужен; TTL обеспечивает требование спеки FR-013; при пустой/истекшей памяти fallback детерминирован — последняя трата пользователя по `created_at`.
- **Alternatives considered**: Redis — лишняя инфраструктура для одного процесса; хранить память в PostgreSQL — усложняет простой механизм ради несуществующей персистентности (потеря при рестарте допустима).

## 8. Резолвинг относительных дат

- **Decision**: текущая дата передаётся LLM в системном промпте (из `Clock`); LLM конвертирует «вчера», «позавчера», «в этом месяце», «с 1 по 15 октября» в конкретные даты/диапазон `YYYY-MM-DD` в аргументах тулов; service валидирует формат и диапазон (включительно). Детерминированная проверка — evals на фиксированном reference_time.
- **Rationale**: LLM извлекает параметры (конституция III), арифметика дат в Go ограничена валидацией; фиксированный reference_time делает evals воспроизводимыми.
- **Alternatives considered**: принимать относительные слова в тулах и резолвить в Go — усложняет схемы тулов и размывает контракт; полная арифметика дат на стороне LLM без проверки — риск некорректных диапазонов.

## 9. Веб-панель: React + Vite + TypeScript

- **Decision**: SPA в `web/`; типы API генерируются из `api/openapi.yaml` (openapi-typescript), минимальный fetch-слой; список без пагинации — настраиваемый лимит (query `limit`, дефолт из конфига).
- **Rationale**: типы из контракта исключают ручной дрейф; Vite — минимальная сборка; панель без авторизации по ТЗ.
- **Alternatives considered**: CRA/Next.js — избыточны; ручные TS-типы — дрейф от контракта; серверный рендеринг — не нужен для внутренней панели.

## 10. Evals

- **Decision**: пакет `evals/` с тегом `//go:build eval` (`make eval`, вне CI); датасет `evals/dataset.yaml` — 25–30 кейсов: добавление/просмотр/изменение/удаление, относительные даты, е/ё, сообщения не о тратах, некорректные суммы, изоляция. Время фиксировано через `FixedClock` (reference_time в кейсе).
- **Rationale**: проверяется именно контракт агента «фраза → ожидаемое действие/ответ»; тег сборки исключает evals из обычных тестов и CI (требуют живой LLM).
- **Alternatives considered**: гонять evals в CI — нестабильно и платно; проверять только юнит-тестами оркестратора — не ловит качество реального LLM.

## 11. Интеграционные тесты (ADR-007)

- **Decision**: `make test` поднимает/переиспользует PostgreSQL из docker compose и гоняет интеграционные тесты против реальной БД (миграции goose применяются тестовым раннером).
- **Rationale**: проверки scoping и upsert требуют настоящего SQL (CHECK, FK, ON CONFLICT); без testcontainers — меньше зависимостей, БД и так есть в compose.
- **Alternatives considered**: testcontainers-go — удобен, но добавляет зависимость (конституция VII: только с обоснованием); моки репозитория — не проверяют схему и ограничения.

## 12. Seeding

- **Decision**: при старте, если таблица `users` пуста, создаётся демо-семья (несколько пользователей и трат за текущий месяц) — для мгновенной проверки панели; при непустой таблице seeding пропускается.
- **Rationale**: quickstart-сценарий панели работает «из коробки» после `docker compose up`; идемпотентность — по пустоте `users`.
- **Alternatives considered**: отдельная команда seeding — лишний шаг; без seeding — пустая панель на демо, хуже первому впечатлению.
